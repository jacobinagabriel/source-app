# Plan: source-app (Fork A)

This repo is the source system for the CDC → Iceberg benchmark. The benchmark itself (pipelines, load profiles, measurement) lives in a separate repo, `cdc-iceberg-bench`. The two repos meet only through the contract below.

## Shared decisions

| Decision | Choice |
|---|---|
| Source engine | **Aurora PostgreSQL 17**, provisioned, one writer. Instance class is a variable (default `db.t4g.medium`; a larger class for heavy runs). Fixed capacity keeps benchmark numbers reproducible |
| Gate 0 (done) | Zero-ETL into Iceberg (the SageMaker lakehouse) must work from the source. Result below: RDS for PostgreSQL fails, Aurora PostgreSQL passes |
| IaC | Terraform ≥ 1.11 (ephemeral resources and write-only arguments keep the app password out of state), S3 backend with `use_lockfile = true`, state key `source-app/prod/terraform.tfstate` |
| Environment | `prod` (the account's single environment) |
| Lifecycle | Brought **up** for a benchmark and **down** afterwards by the deploy workflow. Nothing billable remains when down except the ECR images |
| Shared layer | [main-terraform](https://github.com/jacobinagabriel/main-terraform) owns the VPC, the subnets, this app's ECR repository and the IAM permissions boundary, published under `/main-terraform/prod/*` in SSM. `infra/modules/shared` reads them |
| Network placement | ECS tasks in public subnets with a public IP and no inbound rules (no NAT or interface endpoints, so $0 idle network cost); Aurora in private subnets |
| Database users | The Aurora master user (password managed by RDS in Secrets Manager) is the admin and is only used by `source-app db-init`, which creates the app user and its schema. The app connects as that user; its password is generated by Terraform as an ephemeral value and written to Secrets Manager write-only |
| IAM | Every `aws_iam_role` sets `permissions_boundary` to `/main-terraform/prod/iam/app_role_boundary_arn`, and role names start with `source-app-`. AWS enforces both through the deploy role; checkov (`CKV2_CUSTOM_1`) flags it in review |
| CI/CD | GitHub OIDC roles from main-terraform's `bootstrap/github-oidc`: plan comments on PRs; up/down only in the `prod` environment, with your approval |
| Language | Python 3.12, uv |
| ORM and schema | SQLAlchemy 2.0 declarative models; Alembic migrations stored in this repo |
| Tags | `Project=cdc-bench`, `Repo=source-app`, `Component=<x>`, `Pipeline=source` |

## Gate 0 result

Checked against the AWS docs in November 2026:

- **RDS for PostgreSQL** zero-ETL only targets Amazon Redshift (15.11+, 16.7+, 17.3+). The SageMaker lakehouse is listed only for RDS for MySQL. So RDS for PostgreSQL can't put zero-ETL into the Iceberg comparison. See [RDS zero-ETL regions and engines](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.RDS_Fea_Regions_DB-eng.Feature.ZeroETL.html).
- **Aurora PostgreSQL** zero-ETL targets both Redshift and the SageMaker lakehouse in us-east-1, from **16.4+, 17.4+ and 18.3+**. See [Aurora zero-ETL regions and engines](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.Aurora_Fea_Regions_DB-eng.Feature.Zero-ETL.html).

Hence Aurora PostgreSQL 17: all three approaches (DMS, zero-ETL, Debezium) replicate the same source into Iceberg, and DMS and Debezium use plain logical replication either way.

What zero-ETL needs from this repo ([setup](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.setting-up.html), [data types and DDL](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.querying.html)):

- DB cluster parameters, set when the cluster is created (so no reboot):
  - `rds.logical_replication=1`
  - `aurora.enhanced_logical_replication=1`
  - `aurora.logical_replication_backup=0`
  - `aurora.logical_replication_globaldb=0`
- Enhanced logical replication writes full rows to the WAL, so `REPLICA IDENTITY FULL` isn't needed. Toggling it later invalidates every replication slot.
- A primary key on every table. No enum, custom or extension types (`status` and `category` are `text`). `numeric` with explicit precision (`numeric(12,2)`). UTF-8 databases.
- No `ON DELETE CASCADE` foreign keys. The RDS PostgreSQL docs say they put a table in a failed state, and the Aurora docs don't say either way, so the app deletes child rows explicitly.
- At most 5 integrations per cluster. The zero-ETL target (a Glue managed catalog on Redshift managed storage) and the integration itself belong to the bench repo.

## Contract v3 (SSM prefix `/source-app/<env>/`)

| Parameter | Purpose |
|---|---|
| `contract_version` | `3` |
| `vpc_id`, `private_subnet_ids`, `public_subnet_ids` | Where the pipelines run (re-published from main-terraform, so the bench repo only depends on this contract) |
| `db_cluster_arn`, `db_cluster_id` | Zero-ETL integration source, DMS endpoint |
| `db_endpoint`, `db_reader_endpoint`, `db_port`, `db_name`, `db_schema` | Connections, and the zero-ETL data filter (`<db_name>.<db_schema>.*`) |
| `db_engine`, `db_engine_version` | Compatibility checks (`aurora-postgresql`, 17.4+) |
| `db_security_group_id` | The bench repo adds its own ingress rules |
| `db_admin_secret_arn` | Used only by the bench repo's db-setup (replication users, publications) |
| `db_app_secret_arn` | App runtime |
| `schema_version` | Latest Alembic revision applied (written by the deploy workflow after `migrate`) |
| `logical_replication_enabled` | Bench refuses to run if false |
| `db_cluster_parameter_group_name` | Bench checks replication settings |
| `db_max_replication_slots` | Bench checks there is room for its pipelines |
| `db_multi_az` | `false` today; bench skips the failover scenario if false |
| `ecs_cluster_name`, `image_tag` | Which generator is running |

Rules: this repo never creates anything CDC-specific (replication users, publications, slots, integrations). The bench repo only adds things. Teardown order: bench first, then source-app (the down workflow refuses otherwise).

## Phases

**A0. Bootstrap.** Repo, tooling, CI, branch protection.

**A1. Networking (moved to main-terraform).** The shared VPC (2 AZs, public and private subnets, S3 gateway endpoint, NAT and interface endpoints opt-in) lives in main-terraform. This repo reads it from SSM (`infra/modules/shared`).

**A2. Database.**
- An Aurora PostgreSQL 17 cluster with one writer in the private subnets.
- A DB cluster parameter group with the zero-ETL settings above. Replication slots and WAL senders are sized for 3 pipelines plus headroom.
- The master password is managed by RDS. The app user's secret is created write-only.
- Aurora storage grows by itself, so a stuck replication slot costs money rather than filling a disk. Alarms on `TransactionLogsDiskUsage` and `ReplicationSlotDiskUsage` go to SNS.

**A3. Application (v3).**
- No API service: the app *is* the generator, running as the ECS service.
- SQLAlchemy 2.0 models; Alembic migrations in `migrations/`.
- `source-app db-init` (as admin), then `migrate` and `seed`, run as one-off ECS tasks, never on app startup. `seed` does nothing when users already exist.
- Reference data (products, distribution centers) is seeded by an Alembic data migration.
- The generator writes inserts, updates and deletes, one transaction per business action.

**A4. ECS.**
- A Fargate (ARM64) service, plus an ops task definition for the one-off commands.
- `desired_count` is a variable, ignored after creation so pause and resume don't fight Terraform. No ALB.

**A5. Contract outputs.** All SSM parameters above, documented, plus `make contract-check`.

**A6. Operability.** `make pause/resume` (ECS desired count, Aurora stop/start), bench and idle sizes, idle cost documented.

**CD.** `deploy.yml`, run by hand with `up` or `down`, in the `prod` environment:
- `up`: build and push the image (tagged with the git SHA), apply, run `db-init`, `migrate` and `seed`, record `schema_version`, then wait for the service.
- `down`: refuse while `/cdc-iceberg-bench/prod/` has parameters, then destroy.

Rough cost while up in us-east-1: Aurora `db.t4g.medium` ≈ $0.073/h, plus Fargate ≈ $0.015/h including the public IPv4. That's about $0.09/h, or ≈ $2/day. Down: ~$0.

## Code changes (one PR each)

1. Tooling: package layout, uv, ruff, pre-commit, pytest, CI, Dockerfile, README, this plan.
2. Config: remove Kafka arguments, settings from env vars, CLI subcommands `migrate`, `seed`, `run`.
3. ORM + Alembic: declarative models with `uuid`, `timestamptz`, `numeric`, foreign keys; initial schema and reference-data migrations; one transaction per business action (the foreign keys require it). Migrations live in the package (`src/source_app/migrations/`) so the image can run them without extra files.
4. Sampling: indexed random row selection instead of `ORDER BY random()`.
5. Deletes: delete cancelled orders (with their items) and purge old anonymous events.
6. Local dev: docker-compose Postgres with `wal_level=logical`, Makefile, integration test.
7. Infra: read the shared layer from main-terraform.
8. Gate 0 and the move to Aurora PostgreSQL (this document).
9. `db-init`, idempotent `seed`, foreign key without `ON DELETE CASCADE`.
10. Aurora (A2), ECS (A4), contract (A5), deploy workflow: one PR each.
